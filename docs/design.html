Design Document · For Review

talent-promo-eval

A standalone eval harness that answers one question reliably: given the same seed resume and job posting, is this generated resume better than that one? — judged the way real screening works, by an LLM judge we can actually trust.

2026-07-12 · repo: talent-promo-eval · status: draft, pending approval

01 · Why

The problem

The talent-promo app turns (seed resume, job link) into an optimized resume. Each change to the drafting pipeline produces new outputs — but there is no trustworthy way to say "run B is better than run A." Eyeballing doesn't scale, and a naive LLM-as-judge prompt has three known failure modes: it drifts, it can't tell subtle differences apart, and it rewards surface polish (keyword stuffing, confident tone) over substance.

This project builds the judge properly: grounded in research on how resumes are actually screened, trained against comparisons whose correct answer is known by construction, optimized with GEPA, and validated with a discriminative-power gate before anyone trusts its verdicts.

The two-fold rubric

A resume passes through two very different readers, so the judge scores two lenses:

Lens 1 — AI scanner (ATS)

Modern screening software parses, extracts, and ranks before a human ever looks. The judge asks: which version parses cleanly, carries the job's actual vocabulary with evidence behind it, and surfaces a stronger match signal for this posting?

  • Keyword & skill coverage — grounded, not stuffed
  • Parse-friendly structure (headers, sections, no traps)
  • Title/seniority alignment with the JD

Lens 2 — Human skim (3–7 seconds)

Eye-tracking research puts the first human pass at roughly 6–7 seconds, concentrated on the top third: name, current title, most recent role, first bullets. The judge asks: in that window, which version lands the key evidence?

  • Most job-relevant experience above the fold
  • Lead bullets carry quantified, specific outcomes
  • Scannable hierarchy — no walls of text

Both lenses are seeded from a deep-research phase (tech-sector resume standards, how ATS/AI scanners rank in 2025–26, recruiter eye-tracking studies) distilled into docs/taste-guide.md — the domain knowledge the judge prompt starts from.

02 · Architecture

System overview

One pipeline, five stages. Everything downstream of the dataset is automatic because every training pair has a known correct answer.

Corpus snapshot 28 real traces from talent-promo (2 profiles × 14 tech-sector JDs) + human quality codes. One-time copy — no runtime coupling to the app. Kept local-only for privacy; regenerated via the snapshot script.
Degradation engine Controlled perturbations of real resumes, each tagged with the lens it damages (ats / human_skim) and severity (subtle / moderate / severe).
Known-order pairs Comparisons where the winner is known by construction. Split: train (~60–80) / val (~30) / test (~40, never seen by GEPA). Entire degradation types held out of training to test generalization.
Seed judge prompt Hand-written from the taste guide. Baseline accuracy measured before any optimization — GEPA has to beat it.

Cross-provider judging. The app's generator runs on Anthropic models, so the judge runs on OpenAI models (gpt-5-mini as the workhorse, top tier for reflection and the sensitivity sweep). LLMs measurably prefer their own outputs; putting the judge on a different provider removes self-preference bias at the design level.

03 · Data

Known-order pairs: the ground truth machine

GEPA needs a score to climb, and that score is judge accuracy on comparisons we already know the answer to. Three sources, in order of volume:

Synthetic contrast pairs (primary)

Take a real resume, apply one targeted degradation, and you have a pair where the original must win. Deterministic HTML surgery where possible; LLM rewriting only for naturalistic wording changes.

Lens hitDegradationSeverity range
atsStrip or synonym-drift the JD's keywords away from posting vocabularysubtle → severe
atsRemove/rename section headers; bury the skills sectionmoderate → severe
atsDe-quantify bullets (drop metrics, scale, outcomes)subtle → moderate
human_skimPush the most job-relevant experience below the foldmoderate → severe
human_skimBland lead bullets (generic duty statements first, evidence last)subtle → moderate
human_skimWall-of-text bullets; delete the summarymoderate → severe
trapKeyword-stuff beyond source support — the stuffed side must LOSEsubtle → severe

The traps are the anti-gaming mechanism: they teach the judge that better ≠ more keywords, and they punish any rubric GEPA evolves toward surface counting. Subtle-severity pairs are deliberately hard — they're what separates smart judge models from small ones in the tier gate.

Human-anchored pairs (validation only)

Original-vs-generated pairs from corpus traces where human failure codes support a confident ordering. Never trained on — used to check the judge agrees with human judgment, not just with our perturbation engine.

Generalization guard

Entire degradation types are excluded from train/val and appear only in test. If accuracy holds on unseen types, the judge learned resume quality; if it collapses, it learned our perturbation style.

04 · Judge

Single pairwise judge

Pairwise, not absolute scoring: LLMs are unreliable at "is this an 82 or an 87?" but decent at "which is better, and why?" Pairwise verdicts also give GEPA a clean 0/1 reward with no score-drift across generations. One prompt, structured JSON output:

{
  "ats_signal":  { "winner": "A | B | tie", "evidence": "..." },
  "human_skim":  { "winner": "A | B | tie", "evidence": "..." },
  "overall":     { "winner": "A | B | tie",
                   "margin": "slight | clear | decisive",
                   "rationale": "..." }
}

Position-bias control

judge(A, B)First ordering
judge(B, A)Swapped ordering
AgreeConsistent verdict → counted at full weight.
DisagreeInconsistent → penalized in the GEPA metric. High flip-rate rubrics die in selection.

Every judge call is disk-cached by hash(prompt, model, pair, order) — GEPA re-evaluating unchanged candidates costs nothing, and reruns are reproducible. Job inputs accept a URL (fetched, extracted, cached) or raw text.

05 · Validation

The tier-sensitivity gate

The core trick: run the same frozen judge prompt across the OpenAI model ladder on the held-out test set. If the rubric genuinely requires reasoning — weighing grounded evidence against surface polish — smarter models must score higher. If every tier scores the same, the rubric is a checklist any model can pattern-match, and its verdicts carry no signal.

The gate, precisely:

  • Monotone: accuracy non-decreasing up the ladder.
  • Spread: top tier beats bottom tier by ≥10 points on the subtle-severity slice (severe pairs everyone should get; subtle pairs are where reasoning shows).
  • Not noise: McNemar's test between bottom and top tiers, p < 0.05.
  • On failure: the report says so explicitly, and the subtle pairs the top tier missed become GEPA's next training focus. Optional later: the same sweep on the Anthropic ladder as a cross-provider sanity check.
06 · Execution

Phases

  1. Deep research → taste guide → seed prompt Fan-out research with cited sources: tech-resume quality standards, how ATS/AI scanners parse and rank in 2025–26, recruiter eye-tracking behavior. Also pins the current OpenAI model ladder + pricing and the current gepa package API. Output: research-notes.md, taste-guide.md, seed_judge.md.
  2. Scaffold + dataset uv project, corpus snapshot from talent-promo, degradation engine, pair builder, train/val/test splits with held-out degradation types.
  3. Judge harness Pairwise runner with order-swap, structured output, disk cache, job-URL fetcher; metrics module; unit tests against a mocked client, live smoke test behind the env key.
  4. Baseline, then GEPA Seed prompt accuracy on val = the bar. GEPA run with gpt-5-mini as the judged model, top-tier reflection, budget-capped metric calls.
  5. Gates + CLI Held-out accuracy, flip-rate, tier-sensitivity sweep + report. tpe compare-runs for cross-run tracking. README + this doc finalized.

08 · Decisions

Decision log

DecisionRationale
Standalone sibling repoZero imports from the app; consumes triples as files, so it can score any run from any app version.
OpenAI judge, Anthropic generatorCross-provider judging removes LLM self-preference bias by construction.
Pairwise, not absolute scoresTurns a calibration problem into a discrimination problem; clean 0/1 GEPA reward; no scale drift.
gepa package, not DSPyReference implementation; the judge prompt stays a directly-authored text artifact, which is the point of the taste guide.
Hybrid ground truthSynthetic known-order pairs give volume + automatic scoring; human-coded corpus anchors keep it honest.
gpt-5-mini as workhorse judgeCheap enough for GEPA's many rollouts; the tier sweep then shows how much the rubric gains from stronger models.
